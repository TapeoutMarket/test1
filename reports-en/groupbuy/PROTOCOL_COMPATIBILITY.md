# Protocol Compatibility and Evidence Boundaries

This file describes the actual constraints of this repository's candidate implementation. Source code, successful compilation, local tests with simulated assets, local integration of real protocol sources, a real-chain state fork and mainnet receipts are different evidence categories. This round used a read-only BSC RPC to fork real state at block `128554249` locally and executed a lifecycle with a signature-free order validated inside the fork on Seaport 1.6. Subsequent direct-claim diagnostics found that a zero pending value must not prevent claim; the corrected continuing-rewards regression passed, including a positive actual receipt from another harvest after pending=0. No private-key signatures or mainnet broadcasts were used. Importing existing public market orders, mainnet deployment and UI integration remain unexecuted; fork results must not be reported as mainnet readiness or passage of a security audit.

## 2. Compilation, deployment identity and callers

The project's Factory, Vault and MarketValidator use Solidity 0.8.24, Paris, via-IR, optimizer 200 and OpenZeppelin contracts / contracts-upgradeable 5.4.0. Shared reentrancy protection uses ordinary storage and does not depend on transient storage. Actual runtime byte counts, the full compiler version, source hash, ABI / codehash are determined by the generated `RELEASE_MANIFEST.json` and contract report; the EIP-170 code-size limit was not raised.

Vault is an ERC-1167 clone pointing to an ordinary fixed logic contract. Template initialization is locked, and Factory clones and initializes in the same transaction. The template's `implementationSelf()` is a constructor immutable; Factory checks the template identifier, initialization lock, approved codehash and configuration version together, rejecting standard upgrade proxies misidentified as fixed templates. For ERC-1167, see [ERC-1167](https://eips.ethereum.org/EIPS/eip-1167) for the fixed forwarding target definition. Governance can still approve a malicious new template, so these checks do not replace source review and independent codehash verification of future templates.

To fit actual code-size limits, the template constructor creates a stateless `MarketValidator` once, with its address fixed as an immutable. Vault uses only read-only STATICCALL to it; the validator has no owner, upgrade, asset-receiving or purchase-execution capability, does not consult Factory's latest configuration, and does not choose an implementation through a dynamic registry / delegatecall. Purchases are direct **Vault → fixed market** calls, and Mining is likewise called by **Vault → fixed Mining**. The template and its fixed validator are both executable code that must be audited, verified and archived; upgrading Factory does not replace an existing Vault's validator.

## 3. Seaport: an explicit fixed-price subset

The accepted order has one non-criteria ERC-721, quantity 1, FULL_OPEN, and zero zone / zoneHash / conduitKey. Only two fixed-amount native-currency consideration items are accepted: seller proceeds first and a 1% buyer fee rounded down second. Both recipients, amounts and order enter the commitment. `totalOriginalConsiderationItems` must be 2. ERC-20, WBNB, variable-price auctions, criteria, restricted, partial, nonzero conduit, arbitrary aggregate calldata and extra tips are rejected.

The order structure, counter and requirement to check approval to Seaport itself when conduit is zero follow the official [Seaport Models](https://docs.opensea.io/docs/seaport-models). The project's additional two-payment and 1% rules come from this round's specification; this does not claim that all Seaport orders have that structure.

Saved and checked identity includes configured chainId=56, market address / codehash, the actual domain and version returned by `information()`, seller, all OrderComponents and signing counter, orderHash, all execution parameters, and the `keccak256` of the full signature payload. The domain is also recomputed from the Seaport name, actual version, chainId and verifyingContract rather than trusting the supplied domain alone. Order bytes must be canonical `abi.encode(Types.Order)`, without trailing fields.

Signatures support EOA 65-byte, EIP-2098 64-byte, ERC-1271, or a validated order already recognized by Seaport; additional bulk-order signature wrappers are not implemented. Bulk signatures that have not been prevalidated on-chain are outside V1's supported scope. `isValidated` does not replace checks for cancellation, counter, time limits, full fill, ownership or approval. After binding terms/hash/domain, explicit cancellation, counter changes and full-fill facts are classified before current signature availability, so that an ERC-1271 seller's later signature revocation cannot hide an already confirmed cancellation. Signature invalidity alone remains UNKNOWN and cannot independently cause permanent termination.

The deadline fixed at initialization must be no later than order endTime minus a **positive** safetyMargin and later than startTime. An order that has not started may have an empty pool created, but cannot accept contributions. The fixed order is checked again before purchase; after purchase, `ownerOf == Vault`, Seaport success, size>0 and filled==size for that orderHash, and no cancellation are all required. Initial 0/0 is not considered fully filled.

| State | New contribution / purchase | Public permanent termination |
|---|---|---|
| Individual cancellation, counter change, size>0 and fully filled, expiry | Reject | May terminate the current FUNDING pool |
| Not yet started | Reject | Do not terminate merely because it has not started |
| NFT approval revoked | Reject | Consider recoverable; do not end automatically |
| NFT owner is no longer the fixed seller | Reject | Ownership change alone is not permanent cancellation |
| Call failure, signature state cannot be confirmed, abnormal read | Reject and show UNKNOWN | Do not treat as cancellation; holders may still exit themselves or refund after expiry |

A public valid listing and signature payload may be fulfilled by a third party; there is no guarantee that only test wallets can buy. If another person buys the public order first, the final contribution and its mint revert atomically; prior participants can still withdraw principal themselves.

## 4. Version limits of local real Seaport

`seaport-core@1.5.0` and `seaport-types@0.0.1` are locked (source metadata points to official [seaport-core](https://github.com/ProjectOpenSea/seaport-core) and [seaport-types](https://github.com/ProjectOpenSea/seaport-types)) and independently compiled by `scripts/build-seaport.mjs` with `solc@0.8.17`, London, via-IR and optimizer 200. `fixtures/seaport/BUILD.json` contains the actual compiler version, each input source's SHA-256, settings and runtime code size. `Seaport.json` / `ConduitController.json` are artifacts of those real sources, not a MockSeaport that always returns true.

The compiler versions are separated to reproduce the compilation requirements of this real protocol source set, not to downgrade the candidate Vault compiler. The test VM uses chainId 56 for domain consistency of locally constructed orders; **a local VM with chainId 56 is neither BSC mainnet nor a real-chain state fork**.

The local 1.5.0 artifact tests and BSC fork are separate evidence sets. At fixed BSC block `128554249`, `information()` on `0x0000000000000068F116a894984e2DB1123eB395` returns 1.6; the deployed runtime in the Sourcify verification record matches that block's RPC code hash, and the record identifies it as non-proxy. The signature-free order lifecycle validated inside the fork passed on that deployed bytecode; see [identity verification](docs/REAL_PROTOCOL_IDENTITY_REVIEW.md) and the [actual fork report](../../reports/real-bsc-fork-tests.json). This result does not cover newer versions, future blocks or existing public market orders; subsequent orders still require actual domain/version, market codehash, counter, approval and verification-block checks.

## 5. Official CircuitMarket: real path disabled by default

The specification's proxy `0x6feEbbEbC07BcB90bd1Ac8b0CF9BaA4f0fF2B46f` and historical implementation `0x725771c38361abEF7b844729B978c775F7A83dFb` are historical leads only. This round did not verify that proxy's current implementation, actual complete ABI, fee settlement, custody model, recipient address or getter / seal semantics.

Therefore, `MarketKind.CIRCUIT_RESERVED` is rejected by Factory and purchase logic; an unknown version is not presented as compatible. `IMockCircuitMarket` and `MarketKind.MOCK_CIRCUIT` are explicitly local models only, with `mockOnly=true` enforced. In the local model's `listingView`, active means the listing persists and cannot mechanically be equated with valid in the real API; listingPrice in the model is the buyer's exact total payment. This definition must not be copied to production before the real ABI is confirmed.

Mock tests cover fixed listingId, seller / collection / tokenId, price and fee snapshots, cross-checks against listingFor, revocation and restoration of approval, repricing, relisting, unknown reads, purchase rollback and wrong-NFT delivery. Native expiry has not been invented; a separate deadline always exists. Quote `quoteExpiresAt` is only an off-chain TTL and does not decide permanent on-chain cancellation.

A future real adapter must verify queries and purchases at the proxy itself, not buy from the implementation. A fixed proxy address / codehash cannot prove the implementation is unchanged; Vault cannot use its own SLOAD to read another contract's EIP-1967 slot. Without reliable on-chain getter / seal evidence, RPC identity checks are only off-chain preflight and cannot eliminate residual risks such as proxy upgrades earlier in the same block. Even when implementation is queryable, getter and permission semantics still require review. At this stage, this is a live-chain release blocker.

## 6. NFT, Mining and BEM

Local MockNFT is a standard ERC-721 model; purchase tests cover ordinary transferFrom as well as safe receipt and ownerOf postconditions. Purchase and redemption of TapeOut #3204 were also executed on a real fixed-block BSC fork; the Collection Beacon and implementation at that block were resolved, see [identity verification](docs/REAL_PROTOCOL_IDENTITY_REVIEW.md). These specific paths do not prove all NFT upgrade permissions, special transfer restrictions or mining eligibility rules.

The Mining interface is `minerKey(address,uint256)`, `pending(bytes32)`, `claim(bytes32)`. Vault reads the key from the fixed Mining contract rather than guessing the production key encoding. At the real fixed block, key, pending, implementation address and owner/isSealed/paused were read, and the actual fork path in which Vault calls Mining and receives positive BEM was executed. The [independent settlement diagnostic](../../reports/real-mining-settlement-f2b486c2-14e2-4034-a43a-e80c61b40974-1792413996165.json) further confirmed that A received `37601` raw BEM after directly calling Mining when pending=0. This disproved the old assumption of skipping claim when pending is zero. The corrected rule calls the fixed Mining.claim on every harvest and accounts only actual receipts; real errors revert unchanged rather than being disguised as a successful claim of 0. The corrected Vault continuing-rewards regression passed; before the second harvest, pending=0, while new actual receipts and the totalAccounted increment were both `37601` raw. Full Mining caller authorization, recipient rules, accrual and upgrade-permission semantics remain UNKNOWN; this counterexample does not establish that pending's entire internal implementation is merely a particular storage field.

MockBEM uses 8 decimals, and real BEM was also read at the fixed block as `decimals() = 8`, `minter() = Mining`; the contract ledger always works in raw integers without hardcoding 8 or 18 in reward calculations. The actual fork checked Vault receipts, wallet balance deltas and claims after transferring IDs with positive rights. Whether every BEM path is non-rebasing, fee-free and free of privileged balance changes remains UNKNOWN. Payments check both Vault balance decrease and recipient balance increase; transfer fees, abnormal decreases or transfer failures revert the transaction. Positive rebases cannot reliably be distinguished from ordinary receipts through balance reconciliation alone, so full token semantics still require a source audit.

Ordinary claimBatch syncs and claims only BEM actually received in Vault and does not require Mining to work. Harvest first syncs existing direct transfers, then calls Mining from Vault and checks new receipts. Entitlement is cumulative per-ID rights minus that ID's claimed amount, not current balance times the holding ratio. The ERC-1155 standard provides batch transfer / balance facilities; the project's batch reward and redemption rules are separate business logic and cannot be inferred from the standard alone. [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155)

After redemption of all 100 IDs, only the fixed redeemedBeneficiary can claim late BEM. redeemWithoutHarvest calls neither Mining nor BEM, merely closing, burning shares and delivering the NFT; unpaid amounts are not recorded as paid. It still depends on the underlying NFT allowing transfers and cannot bypass failures in that NFT itself.
